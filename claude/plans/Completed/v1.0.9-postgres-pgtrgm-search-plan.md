# v1.0.9 — PostgreSQL + pg_trgm Search Improvements

**Status:** plan only, written 2026-07-30 against app version `1.0.8`
**Scope:** faster, typo-tolerant, Arabic-friendly search using only PostgreSQL. No new services.

---

## Context — what search does today

Every search box in the app is the same Prisma pattern:

```ts
{ name: { contains: search, mode: 'insensitive' } }
```

Prisma emits `ILIKE '%term%'`. A leading wildcard means **no btree index can ever be used**, so every search is a sequential scan over the whole table plus a per-row case fold. It is correct, and it is fine at today's data volume — but nothing about it improves, and it cannot tolerate a typo or an Arabic spelling variant.

Confirmed search sites:

| Area | File | Columns searched |
|---|---|---|
| Customers | `backend/src/repositories/customers.repository.ts` | `name`, `phone` |
| Ledger | `backend/src/features/financial/ledger/financial-ledger.repository.ts` (`customerWhere`) | `customer.name`, `customer.phone` |
| Suppliers | `backend/src/features/suppliers/suppliers/suppliers.repository.ts` | `name`, `phone`, `companyName` |
| Supplier ledger | `backend/src/features/suppliers/transactions/supplier-transactions.repository.ts` (`supplierTransactionWhere`) | `description`, `reference`, `supplier.name`, `supplier.companyName` |
| Prepaid | `backend/src/features/financial/prepaid/prepaid.repository.ts` (`buildWhere`) | `description`, `customer.name`, `customer.phone` |
| Products | `backend/src/features/service/products/products.repository.ts` | `name`, `model`, `brand`, `barcode` (startsWith) |

Raw SQL precedent already exists (`prisma.$queryRaw` tagged templates in `dashboard.service.ts`, `app.ts`, `diagnostics.service.ts`), so this is not a new technique for the codebase.

---

## The central design decision — two phases, not one

**pg_trgm GIN indexes accelerate `LIKE`/`ILIKE` directly.** That means the biggest win requires **zero application code changes**: add the indexes, and every existing Prisma `contains` + `insensitive` query becomes index-backed.

This plan therefore splits into:

- **Phase A (CP2, CP4–CP6 index work)** — indexes only. No query changes, no behavior changes, no new endpoints. Instantly reversible with `DROP INDEX`. This is where ~90% of the value is.
- **Phase B (CP3, CP4–CP6 ranking work)** — normalization function + `similarity()` ranking + typo tolerance via targeted raw SQL. Higher risk, opt-in per endpoint, behind a flag.

**Ship Phase A even if Phase B slips.** If any checkpoint runs long, cut Phase B and release; the indexes alone justify v1.0.9.

- New: `backend/src/lib/search-normalize.ts` (+ `.test.ts`)

### The unaccent trap — read before choosing

`unaccent()` is declared **STABLE, not IMMUTABLE**, because its behaviour depends on a dictionary that can be reconfigured. PostgreSQL therefore refuses it in an index expression. The common workaround — wrapping it in a hand-declared `IMMUTABLE` function — is *lying to the planner*: if the dictionary is ever changed, existing indexes become silently wrong.

**Recommendation: do not use `unaccent`.** Its default ruleset targets Latin scripts and does almost nothing for Arabic, which is the case that actually matters here. Use `translate()` and `regexp_replace()` instead — both are genuinely `IMMUTABLE` and safe in index expressions.

### Proposed SQL function

```sql
-- Arabic/English search normalization. IMMUTABLE so it can be indexed.
CREATE OR REPLACE FUNCTION hc_search_normalize(input text)
RETURNS text AS $$
  SELECT translate(
    regexp_replace(
      lower(coalesce(input, '')),
      '[ً-ْـ]',   -- tashkeel (harakat) + tatweel
      '', 'g'
    ),
    'أإآٱىة',                     -- alef variants, alef maqsura, taa marbuta
    'اااايه'
  );
$$ LANGUAGE SQL IMMUTABLE STRICT PARALLEL SAFE;

-- Digits-only phone form, so "70 123-456" matches "70123456".
CREATE OR REPLACE FUNCTION hc_phone_normalize(input text)
RETURNS text AS $$
  SELECT regexp_replace(coalesce(input, ''), '[^0-9]', '', 'g');
$$ LANGUAGE SQL IMMUTABLE STRICT PARALLEL SAFE;
```

**Tradeoffs to state explicitly in the migration comment:**

| Rule | Benefit | Cost |
|---|---|---|
| Strip tashkeel/tatweel | "مُحَمَّد" matches "محمد" | none in practice — diacritics are rarely typed |
| Unify alef forms (أ إ آ ٱ → ا) | "أحمد" matches "احمد" | none in practice — this is the single highest-value rule |
| ى → ي | "مصطفى" matches "مصطفي" | none in practice |
| **ة → ه** | "فاطمة" matches "فاطمه" | **changes meaning in some words.** Users almost always want this in a search box. Keep it, but note it. |
| `lower()` | English case-insensitivity | none — Arabic has no case |

**`CREATE OR REPLACE FUNCTION` is not safe to re-run once indexes depend on it.** If the body changes, every dependent index must be reindexed or it returns wrong results. Treat the function as append-only: if the rules ever need changing, create `hc_search_normalize_v2` and migrate indexes to it.

### TypeScript mirror

`backend/src/lib/search-normalize.ts` must implement byte-identical logic:

```ts
export function normalizeSearchTerm(input: string): string
export function normalizePhoneTerm(input: string): string
export function escapeLikePattern(input: string): string  // escapes % _ \
```

Its test file must assert the same inputs produce the same outputs as the SQL function, with a table of Arabic cases (`أحمد`/`احمد`, `مُحَمَّد`/`محمد`, `فاطمة`/`فاطمه`, `مصطفى`/`مصطفي`).

**Verification**
```sql
SELECT hc_search_normalize('أحمد') = hc_search_normalize('احمد') AS alef_ok,
       hc_search_normalize('مُحَمَّد') = hc_search_normalize('محمد') AS tashkeel_ok,
       hc_search_normalize('فاطمة') = hc_search_normalize('فاطمه') AS taa_ok,
       hc_phone_normalize('70 123-456') = '70123456' AS phone_ok;
```
```

```

**Rollback:** `DROP FUNCTION hc_search_normalize(text);` after dropping dependent indexes.

**Stop condition:** all four SQL checks return `true` and the TS tests pass. Do not build indexes on a function whose behaviour is not pinned by tests.

### Phase A — indexes, no code change

```sql
-- Plain-column trigram indexes accelerate the ILIKE '%term%' that Prisma
-- already emits. No application change required.
CREATE INDEX IF NOT EXISTS customers_name_trgm_idx
  ON customers USING gin (name gin_trgm_ops);

CREATE INDEX IF NOT EXISTS customers_phone_trgm_idx
  ON customers USING gin (phone gin_trgm_ops);

-- Normalized expression indexes, for the Phase B queries that call the function.
CREATE INDEX IF NOT EXISTS customers_name_norm_trgm_idx
  ON customers USING gin (hc_search_normalize(name) gin_trgm_ops);

CREATE INDEX IF NOT EXISTS customers_phone_norm_trgm_idx
  ON customers USING gin (hc_phone_normalize(phone) gin_trgm_ops);
```

Then re-run the CP1 baseline `EXPLAIN` and confirm `Bitmap Index Scan` replaces `Seq Scan`.

### Phase B — ranking and typo tolerance

Only if Phase A is green and time allows. Add an opt-in path in the customers repository that uses raw SQL:

```ts
const term = normalizeSearchTerm(rawSearch);
const rows = await prisma.$queryRaw<Array<{ id: string; score: number }>>`
  SELECT id, similarity(hc_search_normalize(name), ${term}) AS score
  FROM customers
  WHERE "deletedAt" IS NULL
    AND (
      hc_search_normalize(name) % ${term}
      OR hc_phone_normalize(phone) LIKE '%' || ${normalizePhoneTerm(rawSearch)} || '%'
    )
  ORDER BY score DESC, name ASC
  LIMIT ${take} OFFSET ${skip}
`;
```

Then hydrate full records by id through Prisma, so serialization stays in one place.

**Rules that are not optional:**
- **Trigram matching needs ≥3 characters.** For 1–2 character terms the `%` operator matches nothing useful. Fall back to the existing `contains` path below a `MIN_TRIGRAM_LENGTH = 3` constant.
- **Phone stays substring, not similarity.** A digit typo in a phone number should *not* match — matching the wrong customer's phone is worse than no result.
- Set the threshold explicitly and per-query rather than relying on the session default:
  ```sql
  similarity(hc_search_normalize(name), $1) > 0.3
  ```
  Prefer this over `set_limit()`, which is session state and interacts badly with connection pooling.

**Verification**
```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT id FROM customers WHERE name ILIKE '%ahmad%' AND "deletedAt" IS NULL;
-- expect Bitmap Index Scan on customers_name_trgm_idx
```
```
npx vitest run backend/src/repositories
```

**Rollback:** `DROP INDEX IF EXISTS customers_name_trgm_idx;` etc. Phase B is behind a length check and a code path — revert the repository file.

**Stop condition:** `EXPLAIN` shows an index scan and existing customer tests still pass. **Result sets must be identical to Phase A**; if Phase B changes which customers are returned for an exact-substring query, stop and reconsider the threshold.

## Prisma raw query safety rules

These apply to every query added in Phase B. Violating any of them is a release blocker.

1. **Use `$queryRaw` tagged templates only.** `` prisma.$queryRaw`… ${value} …` `` compiles each `${}` to a bind parameter (`$1`, `$2`). This is safe.
2. **Never `$queryRawUnsafe` with interpolation.** If it appears in a diff, reject the diff. There is no legitimate use for it in this feature.
3. **Identifiers can never be parameterized.** Table and column names must come from a hardcoded allowlist in TypeScript, never from request input:
   ```ts
   const SORTABLE = { name: 'name', createdAt: '"createdAt"' } as const;
   const column = SORTABLE[input.sortBy];   // never input.sortBy directly
   ```
4. **Build LIKE patterns in SQL, not TypeScript:**
   ```ts
   // safe — the term is a bind parameter, the wildcards are SQL literals
   WHERE col LIKE '%' || ${term} || '%'
   ```
   Never `` `%${term}%` `` in a template that is then interpolated as SQL.
5. **Escape LIKE metacharacters** in the term itself (`%`, `_`, `\`) via `escapeLikePattern`, so a user typing `50%` searches for the literal text rather than wildcarding.
6. **Use `Prisma.sql` / `Prisma.join`** for optional WHERE fragments. Never concatenate strings.
7. **Cap `LIMIT`.** Clamp `pageSize` server-side (existing schemas already max at 100) and pass it as a parameter.
8. **Type the result** (`$queryRaw<Row[]>`) and treat every field as untrusted at the boundary — raw queries bypass Prisma's result typing.
9. **No financial values through raw SQL.** Search returns ids and text only; money continues to flow through the existing Decimal → `moneyToApiString` path. Search must never become a source of financial truth.

## Acceptance criteria

**Functional**
- Searching `احمد` finds customers stored as `أحمد` / `احمد` / `اَحمد`
- Searching `فاطمه` finds `فاطمة`
- Searching `70123456` finds a phone stored as `70-123 456`
- English search remains case-insensitive
- Substring results are a **superset** of today's — nothing that matched before stops matching
- Terms of 1–2 characters still return results via the fallback path

**Performance**
- `EXPLAIN ANALYZE` on each searched table shows `Bitmap Index Scan`, not `Seq Scan`
- Perceived search latency improves; debounce removes per-keystroke queries

**Safety**
- No financial figure changes anywhere — ledger, receivables, supplier, prepaid totals byte-identical
- No data modified, deleted, or reset
- All SQL additive and idempotent
- No `$queryRawUnsafe` anywhere in the diff
- No database credentials in the renderer bundle
- No new runtime dependency and no external service

**Release**
- `release/1.0.9/` contains installer, blockmap, `latest.yml` (v1.0.9), upgrade SQL, README

## Risks and open decisions

| # | Risk | Mitigation |
|---|---|---|
| R1 | Connecting role is not superuser → `CREATE EXTENSION` fails | CP1 stop condition. Fallback: one-off superuser connection, or ship phone normalization only |
| R2 | `hc_search_normalize` is later edited while indexes depend on it → silently wrong results | Treat as append-only; create `_v2` and migrate indexes rather than editing |
| R3 | Phase B changes which rows match, altering a user's mental model | Phase B gated on ≥3 chars and an explicit threshold; acceptance criteria require a superset of today's results |
| R4 | Trigram search on phone matches a wrong customer | Phone uses substring matching only, never `similarity()` |
| R5 | GIN indexes enlarge the database file | Negligible at this scale; note the size delta in the release record |
| R6 | Someone reaches for `CREATE INDEX CONCURRENTLY` and the migration fails | Documented in CP2: Prisma wraps migrations in a transaction; use plain `CREATE INDEX` |
| R7 | `release/v1.0.9` created instead of `release/1.0.9` | Called out in CP9; the v1.0.8 split is the cautionary example |

**Open decisions for the user:**
- **D1** Should ledger search also match the obligation description, or stay customer-only? Product decision; affects whether `debts_description_trgm_idx` is created.
- **D2** Is the `ة → ه` normalization acceptable? It is what users almost always want in a search box, but it does conflate distinct words.
- **D3** Ship Phase A only (indexes, zero code change), or Phase A + B? Phase A alone is a defensible v1.0.9.
