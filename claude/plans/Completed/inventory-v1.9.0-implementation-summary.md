**Prepared:** 2026-08-13

**Repository HEAD:** `9c46f712bec2fb2e13cfbff65e565ab974f251d8`

**Status:** CP-1908 review remediation implemented; re-review pending; changes are uncommitted

## Release purpose

v1.9.0 connects sales-order lines to the append-only inventory ledger. Stock moves only after an
operator explicitly chooses a sales-order line and presses **Deduct Stock / إخراج من المخزون**.
It is never deducted automatically by order creation, confirmation, delivery, payment, debt, or
status changes.

Supplier receiving remains entirely deferred to v1.9.1. This implementation adds no receiving
schema, endpoint, UI, dashboard claim, or supplier-ledger behavior.

## Implemented behavior

### Database

- Added `SalesOrderStockFulfillmentStatus` with `ACTIVE` and `REVERSED`.
- Added `SalesOrderStockFulfillment` with authoritative links to the order, order line, product,
  deduction movement, optional reversal movement, and creating/reversing users.
- Added `DEDUCT_STOCK` and `RESTORE_STOCK` to `SalesAuditAction`.
- Added three CHECK constraints, seven `ON DELETE RESTRICT` foreign keys, regular lookup indexes,
  unique movement links, and a partial unique index allowing only one ACTIVE fulfillment per
  order line.
- Migration is additive and contains no backfill, destructive statement, or protected-table
  alteration.

### Backend

- `POST /sales-orders/:salesOrderId/deduct-stock`
  - ADMIN or EMPLOYEE; no account password.
  - Accepts stored order-item IDs and an optional note.
  - Product, quantity, reference, and reason are resolved/generated by the server.
  - Supports whole-line, multi-line, all-or-nothing deduction.
  - Uses deterministic ordering and chained running balances for repeated products.
  - Rejects manual lines, disabled tracking, missing opening count, orders predating the opening
    count, invalid order status, insufficient stock, foreign item IDs, and duplicate deduction.
- `POST /sales-orders/:salesOrderId/restore-stock`
  - ADMIN only; typed reason required; no account password.
  - Restores only selected ACTIVE fulfillments and records an attributed reversal movement.
- Active fulfillment blocks editing/removing its order line and blocks cancellation/return until
  stock is explicitly restored.
- Per-line inventory state is computed by the backend and serialized to the frontend:
  `NOT_INVENTORY_LINE`, `STOCK_NOT_TRACKED`, `NEEDS_OPENING_COUNT`,
  `PREDATES_OPENING_COUNT`, `ORDER_NOT_ELIGIBLE`, `INSUFFICIENT_STOCK`,
  `ALREADY_DEDUCTED`, `RESTORED`, or `AVAILABLE`.
- Customer, debt, payment, installment, settlement, supplier-ledger, valuation, COGS, FIFO,
  profit, and margin writes remain outside the new paths.

### Frontend

- Added a sales-order inventory panel with bilingual server-owned line states.
- Eligible lines can be selected and deducted explicitly.
- ADMIN can select individual active fulfillments and restore them with a typed reason.
- Deduction and restoration dialogs contain no account-password field.
- Deducted lines have disabled edit/remove actions and explain the restore-first requirement.
- Added an **Orders awaiting stock deduction** dashboard card linked to the matching filtered
  sales-order list.
- Sale fulfillment/restoration movements link back to their source sales order through the
  fulfillment relation, not parsed metadata.

### Operational SQL and documentation

- Added report-only preflight and reconciliation SQL under
  `backend/prisma/repair/inventory-v1.9.0/`.
- No v1.9.0 entry was added to the repair manifest because the rehearsal found no drift needing a
  repair.
- Added v1.9.0 release notes. They correctly state that packaging and the version bump remain
  pending approval.

## Local development-database incident

While the new code was running, `/inventory/summary` briefly returned PostgreSQL `42P01` because
`sales_order_stock_fulfillments` did not yet exist in the local database. The last attached error
preceded migration completion. Migration `20260813160000_add_sales_order_stock_fulfillments`
finished at 17:46:23 local time.

Afterward:

- the physical table existed;
- the migration ledger contained one completed record;
- the live health endpoint reported healthy/connected; and
- the formerly failing awaiting-deduction query succeeded and returned 1 order.

The startup audit established that packaged HomeConnect intentionally starts before pending
migrations so Maintenance can take a verified backup before applying them. The inventory summary
now checks whether the fulfillment table exists. While the migration is pending it returns zero
awaiting orders and loads recent movements without the new fulfillment relations, keeping the
dashboard and Maintenance reachable without auto-applying a migration. Sales-order inventory
actions still require the migration before use.

## CP-1908 independent-review remediation

The first review found that the dashboard awaiting-deduction SQL converted the UTC-naive opening
timestamp in the wrong direction. This did not permit an invalid deduction—the service guard was
correct—but it could overstate the dashboard and filtered list around Beirut midnight. The SQL now
uses `AT TIME ZONE 'UTC' AT TIME ZONE <business timezone>`, matching the TypeScript guard.

A database-gated regression test creates an opening count at 01:30 Beirut, excludes an order from
the preceding business day, and includes one from the opening day. The new action validators are
also strict and use `userTextSchema`, so forged authority fields, HTML, and unsafe control
characters fail at the request boundary instead of being silently stripped or rejected later.

### Legacy product UUID compatibility

Diagnostics then exposed a real-catalogue compatibility issue: product
`02880843-6f16-93fb-2ecc-091af51a07b4` exists in PostgreSQL but Zod's RFC-version-aware
`.uuid()` rejected it. A read-only audit found 40 of 84 local products use canonical PostgreSQL
UUID text with a legacy, non-RFC version nibble. Product data was not rewritten. A shared
`databaseUuidSchema` now accepts PostgreSQL's canonical 8-4-4-4-12 hexadecimal UUID form while
still rejecting malformed and injected values. Product-linked inventory, product, scanner,
service-job, and sales-order validators use that database-compatible schema.
