**Status:** CP-SEC1 → CP-SEC5 complete, **except the CP-SEC5 manual walkthrough**, which needs the
app running and has not been done. No version bump, no installer, no commit.
**Created:** 2026-08-13
**Release target:** **v1.8.1**, shipping before v1.9.0 (sales deduction) and v1.9.1 (supplier receiving).
**Baseline:** v1.8.0, HEAD `f633912`, working tree dirty (see §8)
**Related:** `claude/plans/inventory-v1.9.0-document-linked-movements-plan.md` §5.7.1 — this work

**Scope guard:** this is *not* v1.9.0 inventory-sales work. No sales-order stock deduction, no
supplier receiving, no Financial Truth Foundation, no WhatsApp.

## 0. The policy

Role-based security first. Account password and typed reasons only for high-risk
financial/correction actions. Audit is never removed — only its *reason text* stops being typed by
a human and starts being generated by the server.

## 1. Where product edit requires an admin password

All in `backend/src/features/service/products/products.service.ts`.

| Method | Line | Trigger | Verdict |
| --- | --- | --- | --- |
| `update` | 250 | only when `containsSensitiveProductFields(fields)` | **relax** (non-money fields) |
| `updatePricing` | 213 | always | **keep** — money |
| `updateStock` | 425 | always | **relax** — see §1.1 |
| `setActive` (archive/restore) | 489 | always | **keep** — archive is on the strict list |
| `changeSku` (update + regenerate) | 520 | always | **decision** — see §1.2 |

Every one of these also calls `assertServiceAdmin` first, and the routes are additionally gated by
`requireServiceAdmin` (`requireRole([Role.ADMIN])`). **Removing the password does not open these
to EMPLOYEE** — the ADMIN role check stays exactly where it is.

`containsSensitiveProductFields` (`authorization/service-policy.ts`) currently marks almost
everything `true`. Only `imageUrl`, `notes`, `specifications` and `specificationNotes` are `false`.
So in practice *any* meaningful product edit demands a password today.

### 1.1 `updateStock` does not change stock

Worth stating plainly, because the name misleads: `updateStock` writes only `trackStock` and
`lowStockThreshold` (`products.service.ts:429-433`). It cannot change `stockQuantity` — quantity
moves exclusively through the v1.8.0 inventory ledger. These are configuration flags, not stock
corrections, so the strict-list entries for "stock count correction" and "manual stock removal"
do not cover them. **Recommend relaxing to ADMIN-role-only.**

### 1.2 SKU — a genuine decision, not an oversight

Your list puts "barcode/SKU" under REMOVE. Barcode is easy: it is edited through `update` and
relaxes with everything else. SKU is different — it has its own password-guarded flow
(`changeSku`), it is unique, and it is printed onto physical labels and used by the scanner. A
changed SKU silently invalidates every label already stuck to a box.

**Recommendation: relax the password, keep ADMIN, and add a confirmation step in the dialog that
names the label consequence.** The password was never the right control here — a confirmation the
user actually reads is. Flagged as decision D2 (§10).

## 2. Where product edit requires a typed reason

- **Service layer:** `products.service.ts:241` — `if (!input.reason) throw new ValidationError('Reason is required for sensitive product changes')`.
- **Validator:** `products.validator.ts:127-137` — `updateProductSchema` declares `reason` optional
  then a `superRefine` makes it mandatory whenever a sensitive field is present;
  `:141-142` — stock schema, reason **required**; `:193-194` — SKU schema, reason **required**.
- **Minimum length is 5 characters** (`userTextSchema({ field: 'Reason', min: 5, max: 1000 })`).
  Any server-generated replacement must clear that bar — see §5.

Today's audit fallback is `input.reason ?? 'Product notes updated'` (`products.service.ts:284`),
which is actively misleading: a barcode change with no reason is currently filed as "Product notes
updated". Replacing it with an action-derived string is a correctness fix, not just a friction fix.

## 3. Where service edit/status requires an admin password

All in `backend/src/features/service/service-jobs/service-jobs.service.ts`.

| Method | Line | Trigger | Verdict |
| --- | --- | --- | --- |
| `update` | 105 | only when `containsSensitiveServiceJobFields(fields)` | **relax** |
| `changeStatus` | 143 | only when **not** a routine forward transition | **relax** — see §3.1 |
| `cancel` | 188 | always (route also `requireServiceAdmin`) | **keep** |
| `reopen` | 207 | always (route also `requireServiceAdmin`) | **keep** |

`SERVICE_JOB_FIELD_POLICY` marks everything sensitive except `manualProductName`,
`manualProductModel`, `manualProductBrand`, `manualProductNotes`, `requestedPartName` and `notes`.
So editing a customer, a price, a warranty or a date demands a password today.

Note `update` and `changeStatus` are **not** route-gated to ADMIN — only `cancel`, `reopen` and
`audit` are. Sensitivity there is enforced in the service via `requireSensitiveCredentials`
(`:320`), which calls `assertServiceAdmin` *and* demands reason + password together.

### 3.1 Status changes — relax the password, keep the transition rules

`assertStatusTransitionAllowed` and `isRoutineForwardTransition` (`domain/service-status.ts`) are
doing the real safety work: they refuse illegal transitions outright. The password merely gates
*backward* and *terminal* moves that the transition rules already permit.

**Recommend removing the password from all `changeStatus` calls** while leaving the transition
rules untouched. `cancel` and `reopen` keep both password and typed reason — they are the terminal
actions and they already sit behind `requireServiceAdmin`.

**Open question (D4, §10):** relaxing `requireSensitiveCredentials` on `changeStatus` also drops its
embedded `assertServiceAdmin`, which would let an EMPLOYEE move a job backward. Recommend keeping
an explicit ADMIN check for non-routine transitions — role-based, no password. That is the policy
working as intended, not an exception to it.

## 4. Where service edit/status requires a typed reason

- **Service layer:** `requireSensitiveCredentials` (`service-jobs.service.ts:320-323`) — reason and

- **Validator:** `service-jobs.validator.ts:101-102` (update) and `:110-111` (status) declare both

## 5. Which audit services depend on reason

**`writeServiceAudit` (`features/service/audit/service-audit.ts:6,15`) parses the reason through
`userTextSchema({ min: 5, max: 1000 })` and throws if it is missing, empty, or shorter than five
characters.** `ServiceAudit.reason` is `String @db.Text` **NOT NULL** (`schema.prisma:829`).

Two consequences:

1. **No migration is needed.** The column stays as it is; the server supplies the text instead of
   the user. Every generated string must be ≥5 characters — all the proposed ones are.
2. **Do not weaken `writeServiceAudit`.** Leave the `min: 5` guard exactly where it is. It is what
   will catch a caller that forgets to pass a generated reason, and it is the difference between
   "auto-generated reason" and "no reason at all". `writeSalesAudit` and `writeSupplierAudit` have
   the same shape and are out of scope.

### 5.1 The trap: service-job updates only write an audit when sensitive

`ServiceJobsService.update` wraps its `writeServiceAudit` call in `if (sensitive)`
(`service-jobs.service.ts:106`). Non-sensitive updates write **no audit row at all** today.

If CP-SEC3 simply deletes the `sensitive` branch, it deletes the audit with it — the exact
opposite of the stated policy. **The audit call must be lifted out of the conditional and made
unconditional in the same change.** This is the single highest-risk item in this plan: the friction
removal and the audit preservation are the same edit, and doing half of it silently reduces
coverage.

`ProductsService.update` already audits unconditionally (`products.service.ts:279`), so products do
not have this problem.

### 5.2 Generate reasons on the server, not the client

The uncommitted work (§8) generates reason strings in the browser and posts them. That is weaker
than it looks: a client can post any string, so the audit trail becomes client-controlled text.

**Generate every automatic reason in the service layer**, derived from the action and the changed
field names. The client sends no `reason` at all for these paths. Proposed strings, all ≥5 chars
and bilingual in the house `English / عربي` format:

| Path | Generated reason |
| --- | --- |
| Product details | `Product updated / تم تحديث المنتج` |
| Product barcode | `Product barcode updated / تم تحديث الباركود` |
| Product SKU | `Product SKU updated / تم تحديث رمز المنتج` |
| Product specifications | `Product specifications updated / تم تحديث المواصفات` |
| Product image | `Product image updated / تم تحديث صورة المنتج` |
| Product inventory settings | `Product inventory settings updated / تم تحديث إعدادات المخزون` |
| Service job details | `Service job updated / تم تحديث طلب الصيانة` |
| Service status | `Status changed from <A> to <B> / تم تغيير الحالة` |

The changed-field list is already captured in `beforeValues`/`afterValues`, so the reason string
does not need to enumerate fields — it names the *action*, and the diff carries the detail.

## 9.1 D3 feasibility report — the split is already clean

D3 asked for a report before implementing if separating direct product price fields from pricing
preset/formula logic turned out not to be clean. **It is clean, and it is cleaner than CP-SEC1
assumed.** The separation already exists at the endpoint level, not merely at the field level:

| | Relaxed path | Strict path — untouched |
| --- | --- | --- |
| Schema | `updateProductSchema` (`products.validator.ts:114`) | `updateProductPricingSchema` (`:189`, `.strict()`) |
| Service | `ProductsService.update` (`:229`) | `ProductsService.updatePricing` (`:207`) |
| Data builder | `productUpdateData` (`:547`) | `pricingUpdateData` (`:771`) |
| Fields | name, model, barcode, brand, **price**, **discount**, imageUrl, notes, labelBarcodeSource, specifications, specificationNotes | costPrice, pricingPresetId, useCustomPricing, installmentEnabled, customExpensePercent, customProfitPercent, customDiscountBufferPercent, customInstallmentMarkupPercent, customDownPaymentPercent, customInstallmentMonths, customCalculationMode |

**No field appears on both sides.** `costPrice` and every custom pricing percentage are structurally
unreachable through the relaxed endpoint — `productUpdateData` does not read them and
`updateProductSchema` does not declare them. Preset and formula logic lives entirely on the strict
side and is not modified by this cleanup.

So `price` and `discount` — the product's own selling price and its discount — relax with the rest
of the catalogue fields, per D3's "prefer no password" for direct product fields. Everything the
strict list calls "cost/profit/discount preset logic" stays exactly as it is.

**This supersedes the CP-SEC1 recommendation to split `PRODUCT_FIELD_POLICY` into tiers.** The two
endpoints already *are* the tiers. No tiering work is needed — which removes the largest structural
change CP-SEC2 was going to carry.

One small hardening opportunity, not a requirement: `updateProductSchema` is the only one of the
three product schemas without `.strict()`. Unknown keys are stripped by Zod's default, so a
`costPrice` posted to the relaxed endpoint is silently dropped rather than applied — safe, but
silent. Adding `.strict()` would make it a 400 instead. Cheap, and it removes any doubt about the
boundary above.

## 9.2 The role gate must survive the password removal

A subtlety that cuts **both** ways, and the reason `PRODUCT_FIELD_POLICY` should not be deleted.

`ProductsService.update` calls `assertServiceAdmin` **inside** `if (sensitive)`
(`products.service.ts:239-240`). Non-sensitive edits — `notes`, `imageUrl`, `specifications`,
`specificationNotes` — are open to any authenticated user **today**. `ServiceJobsService.update`
has the same shape through `requireSensitiveCredentials` (`service-jobs.service.ts:320-323`),
which bundles `assertServiceAdmin` + reason + password into one call.

Two failure modes, and a naive edit hits one or the other:

- Delete the `sensitive` branch entirely → cosmetic edits become ADMIN-only. Employees **lose**
  the ability to edit notes, images and specifications. A silent tightening nobody asked for.
- Keep the branch but strip `assertServiceAdmin` along with the password → employees **gain**
  the ability to edit names, prices and barcodes. Exactly what D4 forbids.

**Correct approach: keep `containsSensitiveProductFields` / `containsSensitiveServiceJobFields`
alive as the ROLE gate, and remove only the password and typed-reason checks from the same
branch.** The policy objects change job from "password trigger" to "role trigger". Nothing becomes
dead code, no role boundary moves in either direction, and the diff stays small.

Concretely, `requireSensitiveCredentials` keeps its `assertServiceAdmin` line and loses its other
two, which makes its name wrong — rename to `requireSensitiveRole`.

`service-policy.test.ts` already pins the policy contents and must keep passing unchanged; it is
the proof that no field quietly changed tier.

## 10. Decisions — approved 2026-08-13

- **D1 — Product editing stays ADMIN-only.** Remove the password re-check and the typed reason;
  keep audit with `beforeValues`/`afterValues`, actor, timestamp and action type. Reasons generated
  in the **backend service layer** — the frontend must not send the authoritative audit reason.
  *Implementation note: "ADMIN-only" means the existing role boundary is preserved exactly, not
  widened to cover the four cosmetic fields that are open today — see §9.2.*
- **D2 — SKU changes relaxed.** ADMIN only, no password, no typed reason, backend-generated audit
  reason, plus a UI confirmation:
  `Changing SKU may invalidate printed labels already placed on products. / تغيير رمز المنتج قد يجعل الملصقات المطبوعة سابقًا غير صحيحة.`
- **D3 — Product money fields.** Direct product fields (`price`, `discount`) relax with the rest of
  the `update` endpoint; pricing preset / formula / cost logic stays strict and untouched. **The
  split is clean — see the §9.1 feasibility report.** No `PRODUCT_FIELD_POLICY` tiering needed.
- **D4 — Service job details/status.** Remove password and typed reason from normal updates and
  status changes; keep backend audit with server-generated reasons. Preserve every pre-existing
  ADMIN check — `cancel` and `reopen` keep both password and typed reason as genuinely high-risk
  terminal actions. No employee gains an ability they did not have (§9.2).
- **D5 — `updateStock` relaxed.** ADMIN only, no password, no typed reason, backend-generated
  reason. Real quantity corrections in Inventory (stock count, manual removal, damage/loss,
  verified opening count) stay strict and are not touched.
- **D6 — Version: v1.8.1**, shipping before v1.9.0. Do not bump until CP-SEC5 is approved.
