# v1.9.4 — Supplier Purchase → Inventory Workflow Correction Plan

**Status:** Planning / review only. No code, schema, migration, version, or installer change was made.
**Repo state at review:** `package.json` version `1.9.3`, branch `main`, last release commit `4d24a13`.
**Scope owner decision required before any build starts** (see §20 Open Decisions).

---

## 1. Current Problem Summary

The v1.9.1/v1.9.2 build produced a **technically correct but operationally split** workflow:

| Step | Where | Writes |
|---|---|---|
| 1. Receive stock | `POST /inventory/receiving` | `SupplierReceiving` + `SupplierReceivingItem` + `StockMovement(PURCHASE_RECEIPT)` + `Product.stockQuantity` |
| 2. Record debt | `POST /suppliers/:id/transactions` | `SupplierTransaction(SUPPLIER_DEBT)`, optionally `supplierReceivingId` |

Two user actions, two screens, two mental models, and the money is typed by hand with no relationship to what was actually received. The system knows *what* arrived and *how much is owed*, but never *what was bought at what price*.

**What is actually missing is not a link — the link already exists.** `SupplierTransaction.supplierReceivingId` is already a unique FK to `SupplierReceiving` ([schema.prisma:1072-1073](backend/prisma/schema.prisma#L1072-L1073)). What is missing is:

1. **Line-level purchase data** — quantity × unit price per item. Nothing in the database records a purchase price. `SupplierReceivingItem` has `quantity` only; `SupplierTransaction` has a single lump `amount`.
2. **A single entry point** — one form that produces both records in one financial transaction.
3. **A non-stock purchase line** — "delivery fee", "AC bracket, no SKU" currently has to be a whole separate transaction.
4. **A correction path** — receiving is hard-immutable with no admin recourse.

**Important correction to the framing in the review request:** the desired end state is *not* "replace receiving-first with transaction-first." It is "one command that drives both existing engines." Rebuilding either engine would be the risky move; both are already correct.

## 3. Correct Business Workflow Recommendation

**Recommended architecture: composite command, existing engines untouched.**

```
        ┌──────────────────────────────────────────────┐
        │  Add Supplier Purchase / إضافة فاتورة مورد   │   ← single UI entry point
        │  supplier · receipt no. · date · lines[]     │
        └───────────────────────┬──────────────────────┘
                                │  ONE runFinancialTransaction
             ┌──────────────────┴───────────────────┐
             ▼                                      ▼
   stock lines (kind=PRODUCT)              all lines (money)
   SupplierReceiving                       SupplierTransaction
   + SupplierReceivingItem                 (SUPPLIER_DEBT)
   + StockMovement PURCHASE_RECEIPT        amount = Σ line totals
   + Product.stockQuantity (CAS)                   │
             └──────────── supplierReceivingId ────┘  (existing unique FK)
                                │
                        SupplierPurchaseLine[]   ← NEW: qty, unitPrice, lineTotal
                                                   optional → receivingItemId
```

Rules this architecture enforces by construction:

- **Inventory is written in exactly one place** — the existing `SupplierReceivingsService.create` logic, with its opening-count guard, compare-and-set quantity update, and movement audit. No second stock writer is introduced. Ever.
- **The supplier ledger is written in exactly one place** — `SupplierTransactionsService`.
- **The debt transaction *is* the purchase document header.** No third parent entity.
- **Manual-description lines never touch inventory** — they exist only as `SupplierPurchaseLine` rows with `productId = null`.
- **The old routes stay live and unchanged**, so employees keep receiving stock without supplier-admin rights, and existing supplier payments keep working.

## 5. Existing Product Line Design

**Fields:** product (via existing [ProductPicker.tsx](frontend/src/features/products/components/ProductPicker.tsx)), quantity, unit price, computed line total, optional per-line note.

**Preview shown on selection:** name, SKU, current `stockQuantity`, `trackStock` flag, opening-count status, last known `costPrice`.

**Preconditions checked client-side (advisory) and server-side (authoritative):**

| Condition | Server behavior |
|---|---|
| Product missing | `404 PRODUCT_NOT_FOUND` |
| `trackStock = false` | Reject the *stock* half; offer to record the line as manual-description money only |
| No `OPENING_BALANCE` movement | Reject with existing onboarding message ([supplier-receivings.service.ts:16](backend/src/features/inventory/receiving/supplier-receivings.service.ts#L16)) |
| Purchase date < opening-count date | Reject with existing message ([:17](backend/src/features/inventory/receiving/supplier-receivings.service.ts#L17)) |
| Quantity ≤ 0 or > `INVENTORY_QUANTITY_LIMIT` | `400` |
| Resulting quantity > 2,147,483,647 | `400` |
| Same product twice in one purchase | **Blocked today** by `@@unique([receivingId, productId])` ([schema.prisma:1063](backend/prisma/schema.prisma#L1063)) — see §20 Open Decision D3 |

**Stock is written only when the user leaves "Adds stock to inventory" checked.** Unchecking it produces a debt with priced product lines and no movement — legitimate for goods not yet delivered.

## 6. Quick Product Add Design

This is the only part of the request that touches a security control, so the reasoning is spelled out.

The opening-count gate exists because a product that has been sitting in the shop has an **unknown true physical quantity**, and letting stock movements start from an unverified baseline silently corrupts the count. That risk **does not exist for a product created seconds ago inside this form** — its true prior physical stock is zero as a matter of fact, not as a guess.

**Recommended (Option 1 — allow, tightly fenced):**

- Admin role only, plus the existing `verifyAdminPassword` call with action `VERIFY_OPENING_COUNT` — the same audited path used by [InventoryService.verifyOpeningCount](backend/src/features/inventory/inventory.service.ts#L50-L104). No new bypass, no new privilege.
- Server creates: product (`trackStock: true`) → `OPENING_BALANCE` movement of **0** → then the `PURCHASE_RECEIPT` line, all in one transaction.
- Guard: zero-opening is permitted **only** for a product created inside the same transaction. The service must verify the product has no pre-existing movements and was not supplied by id. A pre-existing product with no opening count is still rejected exactly as today.
- Fields required: name, model, quantity, unit price. SKU auto-generated by existing SKU service; barcode, brand, selling price optional and editable later on the product page.

**Fallback (Option 2 — conservative):** quick-add creates the product only; the line is saved as money-only and the purchase page shows *"Needs opening count before stock can be received."* Choose this if the fence in Option 1 is judged too subtle to maintain.

**Never acceptable:** creating a product and receiving stock into it without an admin password, or writing an `OPENING_BALANCE` for a product that already existed.

## 7. Manual Description Line Design

**Fields:** description (required, 3–500), amount (required, positive money), optional note.

**Behavior:** no product created, no product resolved, no `StockMovement`, no `Product.stockQuantity` change, no receiving item. The line is a `SupplierPurchaseLine` with `kind = MANUAL`, `productId = null`, `receivingItemId = null`. It contributes to the debt total only.

**A purchase composed entirely of manual lines must not create a `SupplierReceiving` at all** — an empty receiving document with zero items is a data-integrity trap and the current validator already rejects zero-item receivings ([supplier-receivings.service.ts:97](backend/src/features/inventory/receiving/supplier-receivings.service.ts#L97)).

## 8. Receipt / Invoice Number Design

**Recommendation: option 3 — both fields, transaction is authoritative, propagated on write.**

- Add `SupplierTransaction.receiptNumber String?` (indexed). Do **not** overload the existing `reference` field: it is already in use for payment references (bank slip, cheque no.) and conflating the two makes ledger search ambiguous.
- The composite command copies the value into `SupplierReceiving.referenceNumber`, which already exists and already backs the duplicate-check endpoint `GET /inventory/receiving/duplicate-check`.
- **Warning, never a unique constraint.** Real suppliers reuse and re-issue numbers; a hard constraint would block a legitimate purchase at the counter with no override. Duplicate detection is scoped `(supplierId, receiptNumber)` and surfaces as a dismissible inline warning showing the matching document — the same pattern already implemented in [`SupplierReceivingsService.duplicateCheck`](backend/src/features/inventory/receiving/supplier-receivings.service.ts#L85-L89).
- **Duplicate *posting* is prevented structurally, not by the receipt number**: `SupplierTransaction.supplierReceivingId` is `@unique`, so one receiving can never carry two debts.

**Rejected: a new `PurchaseDocument` parent entity.** It would add a third header table over two tables that are already 1:1-linked, require backfilling every existing receiving and transaction, and duplicate `supplierId`/`date`/`amount` in a third place — three new ways for the ledger and inventory to disagree. The debt transaction is the header.

## 9. Price / Estimated Price Design

`Product.costPrice` already exists and is already the **authoritative purchase-cost input to the pricing engine** ([pricing-resolution.ts:13-28](backend/src/features/pricing/calculator/pricing-resolution.ts#L13-L28)). That makes it the correct and only honest source for a suggestion.

**Rules:**

- Suggest `product.costPrice` as the unit price, labeled *"Last recorded cost / آخر كلفة مسجلة"* — pre-filled but always editable, and clearly not a prediction.
- If `costPrice` is null, suggest nothing. Leave the field empty.
- **Never derive a cost suggestion from the selling price**, and never run the expense/profit/buffer configuration backwards to invent one. The user asked for an estimate "without expense/buffer" — the last recorded cost is exactly that.
- **Never write `costPrice` back** from a purchase in this release. Cost updating changes every downstream price the pricing engine produces and belongs to the deferred financial foundation.
- **Debt amount = Σ (quantity × unit price)** from user-entered numbers only. An override of the total is allowed (freight, rounding, supplier discount) but requires a typed reason stored on the transaction and the line sum is retained for audit.
- No COGS, no inventory valuation, no weighted average cost. Out of scope, explicitly.

## 10. Receiving / Inventory Connection Design

The composite service reuses the existing receiving logic verbatim. For each `PRODUCT` line with stock enabled, inside one `runFinancialTransaction`:

1. Validate product, `trackStock`, opening balance, date ordering, quantity ceiling.
2. `InventoryRepository.compareAndSetQuantity(id, before, after)` — the existing optimistic-concurrency update; `count !== 1` → `409 STOCK_CHANGED`.
3. Create `StockMovement` with `movementType: PURCHASE_RECEIPT`, `referenceType: 'SUPPLIER_RECEIVING_ITEM'`, `referenceId: <itemId>`.
4. Create `SupplierReceivingItem` with the pre-generated `itemId` and `stockMovementId`.
5. Link the `SupplierPurchaseLine` to that `receivingItemId` (unique).

Then create the `SUPPLIER_DEBT` transaction with `supplierReceivingId` set, and write the supplier audit row.

**Anti-duplication invariants:**

| Risk | Structural defense |
|---|---|
| Double stock increase | `SupplierReceivingItem.stockMovementId @unique` + `SupplierPurchaseLine.receivingItemId @unique` |
| Double debt for one delivery | `SupplierTransaction.supplierReceivingId @unique` (already present) |
| Partial write on failure | Single `runFinancialTransaction` — all or nothing |
| Concurrent receive of same product | Compare-and-set on `stockQuantity`, already implemented |
| Manual line silently moving stock | `productId = null` makes a movement impossible to construct |

## 11. Admin Edit / Delete / Correction Design

**Direct answers to the six questions raised:**

1. **Is edit/delete safe after stock increased?** No. A raw edit of quantity leaves `StockMovement.quantityBefore/After` lying about history, and a raw delete leaves `Product.stockQuantity` inflated with no trace.
2. **How should stock be corrected on edit?** Not by mutating the original — by posting a compensating movement.
3. **Should delete decrease stock?** A *reversal* should. A *delete* should not exist.
4. **What if stock was already sold?** The reversal must be blocked when it would drive `stockQuantity` negative, with a message naming the shortfall.
5. **Audit required?** Full: who, when, typed reason, before/after balances, and the linking movement — matching the existing supplier audit shape.
6. **Call it edit/delete or correction?** **Call it "Correct" and "Void" in the UI; implement it as reversal underneath.**

**Recommended pattern — mirror `SalesOrderStockFulfillment`, which already solves this exact problem** ([schema.prisma:947-970](backend/prisma/schema.prisma#L947-L970)): it carries `status`, `reversalStockMovementId @unique`, `reversedAt`, `reversedById`, `reversalReason`. Copy that shape onto `SupplierReceivingItem`. No new invention, no new concept for the team to learn.

**Admin correction flow:**

- **Void a purchase** → for each item, post a compensating `MANUAL_REMOVE` movement (reason: `Receiving reversal — <receipt no.>`), mark the item `REVERSED`, mark the receiving `VOIDED`, and `REMOVE` the linked debt transaction via the **existing** remove path (password + typed reason + audit, already built at [supplier-transactions.service.ts:76-91](backend/src/features/suppliers/transactions/supplier-transactions.service.ts#L76-L91)).
- **Correct a purchase** → void + repost as a new purchase referencing the original. The UI presents this as an edit; the database records two documents and a link. This is the only way an "edit" can be honest about stock that moved in between.
- **Blocked** when any product's stock would go negative → `409 REVERSAL_WOULD_GO_NEGATIVE` naming the product and shortfall, with the suggestion to correct the count separately first.
- Admin role + `verifyAdminPassword` + typed reason (min 5 chars) on every reversal, consistent with every other guarded inventory action.

**UI change:** delete the immutable banner at [SupplierReceivingDetailPage.tsx:33](frontend/src/features/inventory/receiving/pages/SupplierReceivingDetailPage.tsx#L33). Replace with a status chip — *Posted / مُرحَّل* or *Voided / ملغى* — plus **Correct** and **Void** buttons for admins, and a visible correction history. The owner gets full control; the ledger keeps its spine.

## 12. Ledger Separation Rules

Non-negotiable, unchanged by this release:

- Supplier purchases and receivings **never** write customer receivables, sales orders, or customer payments. There is no code path between them today and none is added.
- `SUPPLIER_DEBT` → `INCREASE_OWED`. `SUPPLIER_PAYMENT` → `DECREASE_OWED`. Direction resolution stays in `resolveSupplierDirection`; the composite command does not compute direction itself.
- Receiving stock **never** creates debt implicitly. Debt exists only when the user explicitly saves a supplier-debt purchase. The standalone receiving route continues to create no ledger entry at all.
- Supplier payments create **no** inventory movement, require **no** product, and require **no** receiving. Their code path is not touched.
- Manual-description debt is a first-class, fully valid ledger entry.

## 14. Database Changes Likely Needed

All additive. No column is dropped, no existing column changes type, no existing row is rewritten.

```prisma
// NEW — priced purchase lines, owned by the debt transaction
model SupplierPurchaseLine {
  id                    String   @id @default(uuid()) @db.Uuid
  supplierTransactionId String   @db.Uuid          // → SupplierTransaction, onDelete: Restrict
  kind                  SupplierPurchaseLineKind   // PRODUCT | MANUAL
  productId             String?  @db.Uuid          // null for MANUAL
  description           String                     // snapshot; required for MANUAL
  quantity              Int?                       // null for MANUAL
  unitPrice             Decimal? @db.Decimal(12,2)
  lineTotal             Decimal  @db.Decimal(12,2)
  receivingItemId       String?  @unique @db.Uuid  // → SupplierReceivingItem; the anti-duplicate join
  createdAt             DateTime @default(now())
  @@index([supplierTransactionId])
}

enum SupplierPurchaseLineKind { PRODUCT  MANUAL }
enum SupplierReceivingStatus  { POSTED   VOIDED }
enum SupplierReceivingItemStatus { ACTIVE REVERSED }

// ALTER SupplierTransaction
receiptNumber   String?   // + @@index([supplierId, receiptNumber])
amountOverride  Boolean   @default(false)
amountOverrideReason String? @db.Text

// ALTER SupplierReceiving
status          SupplierReceivingStatus @default(POSTED)
voidedAt        DateTime?
voidedById      String?  @db.Uuid
voidReason      String?  @db.Text
correctsReceivingId String? @db.Uuid   // self-relation, correction chain

reversedAt              DateTime?
reversedById            String? @db.Uuid

```

Backfill: existing rows default to `POSTED` / `ACTIVE`; every new column is nullable or defaulted. Business-PC preflight and reconciliation SQL should follow the pattern already established in [backend/prisma/repair/inventory-v1.9.1/](backend/prisma/repair/inventory-v1.9.1/).

**No money column is added to any inventory table.** Price lives on the purchase line, on the ledger side of the boundary.

## 17. Risks and Safety Rules

| # | Risk | Severity | Mitigation |
|---|---|---|---|
| R1 | Composite command becomes a second stock writer that drifts from the original | **High** | Extract and share one internal function; never copy the logic |
| R2 | Quick-add zero-opening fence leaks onto pre-existing products | **High** | Server asserts the product was created in the same transaction and has zero movements; dedicated regression test |
| R3 | Reversal drives stock negative after goods were sold | **High** | Hard block with named shortfall; never allow negative |
| R4 | Two debts for one delivery | Medium | `supplierReceivingId @unique` (already enforced) |
| R5 | Nested/duplicated transactions on the composite path | Medium | Exactly one `runFinancialTransaction` at the orchestrator; inner services accept `tx` |
| R6 | Employees blocked from a workflow they use daily | Medium | Standalone receiving route stays open and unchanged |
| R7 | Business-PC data volume makes the migration slow or lock-heavy | Medium | All-additive, defaulted columns; preflight + backup gate before applying |
| R8 | Cost/valuation scope creeps in through "estimated price" | Medium | `costPrice` is read-only in this release; write-back is a separate approved release |
| R9 | Amount override becomes a silent way to fake a ledger balance | Low | Boolean flag + typed reason + audit; line sum retained |
| R10 | Same product twice on one invoice hits `@@unique([receivingId, productId])` | Low | Decision D3 below |

**Must not weaken:** opening-count verification, inventory movement audit, supplier ledger audit, customer ledger separation, sales-order validation, role guards, admin password verification.

## 20. Clear Answers

### Build first
**CP-B + CP-C: the schema and the composite purchase endpoint, backend only.** It is the piece everything else depends on, it is testable without any UI, and it proves the one-transaction-two-engines design before a single screen is redrawn.

### Defer
Reversal/void (CP-E), quick-add (CP-G), scanner polish, cost write-back, COGS/valuation, effective-dated corrections, multi-currency, partial deliveries, purchase returns.

### Must not change
The receiving stock-write logic itself; `SupplierReceivingsService`'s opening-count and date guards; supplier payment behavior; `resolveSupplierDirection`; customer ledger and sales-order paths; the scanner; the standalone `POST /inventory/receiving` route and its ADMIN+EMPLOYEE guard; `verifyAdminPassword` on every currently-guarded action.

### The 14 critical questions

1. **Should supplier debt become the main entry point for receiving?** For the **UI**, yes. For the **data path**, no — receiving stays the only stock writer, invoked by the purchase command.
2. **Which creates which?** Supplier debt creates receiving. Never the reverse — receiving must never auto-create debt.
3. **New `PurchaseDocument` model?** **No.** The `SUPPLIER_DEBT` transaction is the header; add `SupplierPurchaseLine` beneath it.
4. **Manual description items?** Line with `kind=MANUAL`, `productId=null`. Money only. No receiving created if all lines are manual.
5. **Existing product items?** Full precondition check → `PURCHASE_RECEIPT` movement → `SupplierReceivingItem` → line links to it by unique FK.
6. **Quick add safely?** Admin + existing password verification, `OPENING_BALANCE` of 0, permitted only for a product created in the same transaction. Fallback: product only, no stock.
7. **Receipt number storage?** New `receiptNumber` on `SupplierTransaction` (authoritative), copied to `SupplierReceiving.referenceNumber`. Indexed, warning-based, never unique.
8. **Can receivings be edited/deleted safely?** Not destructively, ever. Void + repost.
9. **Safe admin correction pattern?** The `SalesOrderStockFulfillment` reversal shape — status + reversal movement + reversedBy/At/Reason + typed reason + password + audit.
10. **Prevent duplicate stock increase?** `stockMovementId @unique`, `receivingItemId @unique`, `@@unique([receivingId, productId])`, compare-and-set on quantity, single transaction.
11. **Prevent duplicate debt?** `supplierReceivingId @unique` (already in production) plus the receipt-number duplicate warning.
12. **Keep ledger and inventory connected but not corrupted?** One writer per side, joined by unique FKs, committed in one transaction, with money kept out of inventory tables entirely.
13. **Scanner POS a separate release?** Yes — and the core of it already shipped in v1.9.3. Nothing scanner-related belongs in v1.9.4–1.9.6.
14. **Safest first checkpoint?** CP-B (schema, additive, defaulted) followed by CP-C (composite endpoint, backend, fully tested before any UI).
